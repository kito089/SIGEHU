# Resumen del Modelo de Base de Datos - SIGEHU (Firebird)

Este documento describe la estructura relacional, la lógica de negocio y las políticas de acceso del sistema SIGEHU. Está diseñado para servir como contexto arquitectónico y permitir la creación o edición de tablas, procedimientos almacenados y lógica de backend (Node.js) / frontend.

## 1. Arquitectura General y Esquema Relacional

El modelo está normalizado y utiliza Firebird como motor de base de datos[cite: 1]. Todas las tablas principales emplean llaves primarias autoincrementales (`GENERATED BY DEFAULT AS IDENTITY`) y mantienen integridad referencial estricta[cite: 1]. 

El esquema se divide en los siguientes dominios principales:

*   **Usuarios y Seguridad**: Gestionado mediante `TiposUsuarios` (Propietario, Trabajador) y `Trabajadores` (almacena credenciales con hash bcrypt)[cite: 1]. Los permisos específicos se manejan mediante `CamposPermiso`, `PermisosGranularesObras` y `PermisosGranularesGarantias`[cite: 1].
*   **Gestión de Clientes**: Las tablas `Clientes` y `ContactosClientes` centralizan la información[cite: 1]. Incluyen catálogos fiscales estándar del SAT (`RegimenesFiscales`, `UsosCFDI`)[cite: 1].
*   **Core / Obras**: La tabla central es `Obras`, la cual vincula al cliente con el estado actual de su proyecto (`EstadosObra`)[cite: 1]. Se complementa con tablas satélite para evidencias (`FotosObras`), comentarios (`NotasObras`), insumos requeridos (`Obras_has_Materiales`) y asignación de personal (`Obras_has_Trabajadores`)[cite: 1].
*   **Inventario y Compras**: Catálogo de `Materiales` y `Proveedores`[cite: 1]. La tabla pivote `Proveedores_has_Materiales` establece los precios por proveedor[cite: 1]. Las adquisiciones se registran en `Compras` (cabecera) y `DetallesCompras` (partidas)[cite: 1].
*   **Finanzas**: El flujo de caja de las obras se registra en `DetallesPagos`, categorizado por `TiposPago` (Efectivo, Transferencia) y `FormasPago` (Anticipo, Parcial, Liquidación)[cite: 1].
*   **Garantías**: Ciclo de vida post-instalación gestionado en `Garantias` (ligado a `EstadosGarantia`), con sus propias evidencias (`FotosGarantias`), comentarios (`NotasGarantias`) y asignaciones (`Garantias_has_Trabajadores`)[cite: 1].

## 2. Sistema de Auditoría (Triggers)

El modelo cuenta con un robusto sistema de auditoría (Módulo M11) incrustado directamente en la base de datos[cite: 1].
*   Las tablas `Auditorias` y `AuditoriasDetalles` registran acciones (INSERT, UPDATE, DELETE) de casi todas las tablas principales[cite: 1].
*   **Regla de Integración (Backend)**: Los Triggers utilizan `RDB$GET_CONTEXT('USER_SESSION', 'CURRENT_USER_ID')` para identificar al autor de la acción[cite: 1]. El backend debe configurar obligatoriamente esta variable de sesión antes de ejecutar cualquier transacción DML[cite: 1].

## 3. Programabilidad (Procedimientos Almacenados y Vistas)

Toda la lógica de transacciones complejas está delegada a procedimientos almacenados para garantizar la atomicidad en Firebird[cite: 1].

*   **Procedimientos Clave**:
    *   `SP_CAMBIAR_ESTADO_OBRA`: Valida si la transición de estado solicitada es permitida según las reglas de negocio antes de aplicarla[cite: 1].
    *   `SP_REGISTRAR_COMPRA_COMPLETA` / `SP_AGREGAR_DETALLE_COMPRA`: Manejan la creación de órdenes de compra[cite: 1].
    *   `SP_ABRIR_GARANTIA` / `SP_CERRAR_GARANTIA`: Encapsulan la lógica para regresar una obra instalada a revisión y posteriormente cerrarla[cite: 1].
*   **Vistas Principales**:
    *   `VW_OBRAS_KANBAN` y `VW_INDICADORES_DASHBOARD`: Optimizadas para alimentar el panel principal de control[cite: 1].
    *   `VW_OBRAS_TRABAJADOR`: Vista de seguridad crucial que filtra exclusivamente las obras asignadas a un trabajador específico, ocultando datos confidenciales, ideal para el consumo desde la app móvil[cite: 1].

## 4. Lógica de Negocio: Máquina de Estados de Obra

El flujo de vida de una obra sigue una secuencia lineal estricta con reglas de retroceso controladas. El cambio de estado es orquestado por el "Propietario", aunque dependa de las confirmaciones operativas del trabajador.

| Estado Origen | Estado Destino Válido | Condición de Transición | Actor Autorizado |
| :--- | :--- | :--- | :--- |
| **Solicitud recibida** | Levantamiento pendiente | Existe cliente, nombre de obra y tipo de elemento. | Propietario |
| **Levantamiento pendiente** | En fabricación | Medidas reales capturadas y aprobadas por el propietario. | Propietario |
| **En fabricación** | Instalación programada | Fabricación confirmada por trabajador; propietario programa fecha. | Propietario |
| **Instalación programada** | Instalado | Equipo de instalación confirma entrega (vía app móvil). | Propietario (Aprueba) |
| **Instalado** | Garantía | Propietario abre un reporte de desperfecto o garantía. | Propietario |
| **Instalado** | Finalizado | No existen reportes de garantía pendientes. | Propietario |
| **Garantía** | Finalizado | Todos los reportes de garantía cambian a estado 'Resuelta'. | Propietario |

*(Nota técnica para el LLM: Las transiciones hacia atrás también están limitadas en `SP_CAMBIAR_ESTADO_OBRA`, permitiendo retroceder solo un paso a la vez, y bloqueando el regreso de obras `Finalizadas`[cite: 1].)*

## 5. Matriz de Seguridad y Control de Acceso (RBAC / ABAC)

El sistema emplea un modelo mixto de Control de Acceso Basado en Roles (Propietario vs. Trabajador) y Control de Acceso Basado en Atributos/Asignaciones (Trabajador con permisos granulares en obras específicas).

| Funcionalidad / Dato | Rol: Propietario (Admin) | Rol: Trabajador (Base) | Rol: Trabajador (Permisos Granulares) |
| :--- | :---: | :---: | :---: |
| **Ver todas las obras** | Sí | No | No (Solo ve obras asignadas) |
| **Ver nombre de obra asignada** | Sí | Sí | Sí |
| **Ver dirección de la obra** | Sí | No | Sí (Si `direccion_instalacion` habilitado) |
| **Ver teléfono del cliente** | Sí | No | Sí (Si `telefono_cliente` habilitado) |
| **Ver precio / presupuesto** | Sí | **Bloqueo Estricto** | **Bloqueo Estricto** |
| **Ver datos fiscales** | Sí | **Bloqueo Estricto** | **Bloqueo Estricto** |
| **Ver medidas (Levantamiento)** | Sí | No | Sí (Si está asignado a fabricación / `medidas`) |
| **Ver catálogo proveedores** | Sí | No | Sí (Si `catalogo_proveedores` habilitado) |
| **Subir fotos / evidencias** | Sí | No | Sí (Si `subir_fotos` habilitado en su etapa) |
| **Confirmar actividades** | Sí | No | Sí (Si `confirmar_actividad` habilitado) |
| **Modificar estado de obra** | Sí | No | No (Depende exclusivamente del Propietario) |
| **Crear/Editar Catálogos/Clientes**| Sí | No | No |
| **Ver Reportes/Auditoría** | Sí | No | No |
| **Gestionar permisos** | Sí | No | No |

**Directrices de Implementación para Backend/Frontend:**
1. **Aislamiento de Datos Sensibles**: La capa de servicio (Node.js) no debe transmitir jamás los campos presupuestales, financieros (`DetallesPagos`) o fiscales si el token de sesión pertenece a un tipo de usuario "Trabajador" (ID 2).
2. **Consultas Restringidas**: Para los trabajadores, la base de datos debe ser consultada preferentemente a través de la vista `VW_OBRAS_TRABAJADOR`[cite: 1] y cruzada con `PermisosGranularesObras`[cite: 1] para construir el payload de la interfaz (ej. habilitar el botón de "Llamar cliente" solo si existe el permiso explícito).
